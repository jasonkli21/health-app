# Phase 1 release evidence

**Date:** 2026-10-03  
**Status:** Implementation complete; independent review remains pending.  
**Scope:** Canonical Profile v1, local principal, PostgreSQL persistence, Profile API/generated client, and a Profile-only mobile flow. This is local development software, not internet-authenticated or production-ready.

## Delivered contract and storage

Profile v1 is the only registered object schema. Its typed payload distinguishes unknown (`value: null`) from known false and zero; numbers must be finite; quantities require an explicit supported unit; and extra or incompatible schema fields are rejected. Validity timestamps must be timezone-aware, are normalized to UTC, and use half-open `[valid_from, valid_to)` intervals. Recorded/revision time remains separate from effective time. Manually saved items are user-confirmed with a server-owned manual source. AI and cross-domain permissions default to false. Relationships are owner-scoped `related_to` service operations only; no generic graph API is exposed.

The PostgreSQL 16.15 disposable integration database reports Alembic head `22dad79c2ee1` (`initial profile persistence`). It contains the six application tables `users`, `sources`, `health_objects`, `profile_items`, `health_object_revisions`, and `health_relationships`, plus Alembic's version table. Owner-consistent composite foreign keys connect objects, sources, revisions, profile rows, and relationship endpoints. Revision uniqueness is `(owner_id, object_id, revision)`; the create fingerprint binds idempotent retries to the original canonical content without reverting later edits. Database checks enforce supported Phase 1 object/schema/status/kind/category/unit-independent shape and validity bounds.

The explicit non-constraint indexes are `ix_health_objects_owner_status_created`, `ix_profile_items_owner_category_key`, `ix_health_relationships_owner_from`, and `ix_health_relationships_owner_to`. Primary-key and owner-scoped unique-constraint indexes include `uq_health_objects_owner_id`, `uq_sources_owner_id`, `uq_sources_owner_key`, `uq_health_object_revision`, and `uq_health_relationships_edge`. A fresh empty disposable database completed `alembic upgrade head`, `alembic downgrade base`, and `alembic upgrade head`; that database was dropped afterward. API test fixtures independently apply the migration to their dedicated test database.

The configured server-only `LOCAL_PRINCIPAL_ID` is the sole local owner identity. A missing principal fails protected requests with 401; request identity headers/bodies cannot select another owner. Foreign and missing item IDs both return 404. The local `AUTH_MODE=dev` does not provide shared or internet authentication. The mobile bundle receives only `EXPO_PUBLIC_API_URL`; it receives no database credentials or principal ID.

## HTTP contract and client

The deterministic tracked OpenAPI document is `contracts/openapi/openapi.json`. Stable operations are:

- `GET /profile`, `POST /profile`
- `GET /profile/{item_id}`, `PATCH /profile/{item_id}`, `DELETE /profile/{item_id}?expected_revision=...`
- `GET /profile/{item_id}/history`
- `GET /healthz` remains public process liveness

Lists default to 50 and cap at 100, and cursor continuation preserves owner/filter/as-of scope. History is revision-paged and capped at 100. Client-generated IDs make retrying create idempotent: first create is 201, identical retry is 200, and different-content reuse is 409. PATCH omissions preserve prior fields while optional dates/notes can be cleared. Every update/archive carries `expected_revision`; stale edits return 409 and the mobile edit flow offers a server refetch. DELETE archives; archived items remain available in owner detail/history and leave the active list.

Request bodies are capped at 65,536 bytes. Responses add `X-Request-ID`; errors use a stable, sanitized typed shape without submitted values or stack traces. Expected errors include 401 missing local principal, 404 unavailable/foreign item, 409 ID/revision conflict, 413 oversized request, 422 invalid contract, and 503 storage unavailable.

OpenAPI remains authoritative for the typed package `@personal-health/api-client`. `services/api/scripts/export_openapi.py` creates the schema without a database request; `packages/api-client/scripts/generate-client.mjs` derives DTOs, operation types, and fetch methods using Node's standard library. Both artifacts are tracked and CI regenerates them and checks for drift. This small repository-owned generator is deliberately limited to the OpenAPI constructs emitted by this service; extend its tested type mapping before introducing another construct. It was selected because registry access was unavailable when choosing a generator dependency.

## Mobile delivery

The shell links only to Profile. The Profile feature includes a category-filtered, paginated overview; create and edit form; provenance/validity/permission detail; archive confirmation; and revision history. The form retains values after request failure and uses the server revision when saving. Unknown, false, zero, list values, and explicit quantity units remain distinct. Date entry requires an explicit timezone. Permission switches visibly default off. The app fetches server truth on focus and does not persist health form data or queue offline writes.

The controls include accessible labels/hints and usable touch targets. Vitest covers generated-client behavior, draft rules, and a static first-render form check. The component check uses test-only native element stubs with React DOM server rendering; it does not exercise native events, keyboard behavior, visual layout, or assistive technology. Those are manual simulator/device release gates. Configure `EXPO_PUBLIC_API_URL` for the target environment; iOS simulator defaults to loopback, Android emulator uses `10.0.2.2`, and physical-device use requires an approved secure private-network endpoint.

## Unresolved release gates and deviations

- The host has Node 24.19 via the Codex-bundled runtime but only pnpm 11.19; the repository pins pnpm 9.15.0. The pinned `pnpm install --frozen-lockfile`, exact root scripts, and full CI workflow therefore remain unverified locally. Tests used the existing workspace install and direct bundled Node tools.
- Docker/PostgreSQL 17 are unavailable locally. Persistence and migrations were verified against PostgreSQL 16.15; CI is configured for PostgreSQL 17.
- No iOS Simulator/device interaction or keyboard/VoiceOver/accessibility walkthrough was performed. A successful Metro bundle is compile evidence, not rendered-device evidence.
- The test environment did not have a React Native component interaction renderer. Rather than introduce an unverified dependency without registry access, mobile automation uses pure model tests and a limited static native-form render; interactive native behavior remains manual.
- The original Phase 0 advisory inventory and dependency source-use review remain unresolved review gates. Passing the Phase 1 tests does not clear them.
- Later-phase identity, cloud, AI, HealthKit/device, Today, and web functions are intentionally absent.
